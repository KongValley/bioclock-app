# BioClock 设计方案 v0.1

> 记录并提醒用户按时注射生物制剂的个人健康工具。
> 技术栈：React Native + Expo，数据纯本地（SQLite），无账号、无服务器、无网络请求。

---

## 1. 定位与边界

**一句话**：把"我上次什么时候打的、下次该什么时候打、该打哪边肚子"这三件事从记忆里搬到手机上，并在到点前提醒你。

**做**：用药方案配置、注射记录、下次时间推算、本地通知、部位轮换建议、症状日志、导出给医生看。

**不做（第一版明确排除）**：

- 不给任何剂量调整、用药禁忌、换药建议 —— 方案参数完全由用户按医嘱如实录入，App 只做算术和提醒。
- 不替代医生。首次启动以及导出报告页都带免责声明。
- 不做账号、云同步、社交、处方识别。

> 合规提示：在中国，涉及"疾病诊断治疗"的功能属于医疗器械软件范畴。本 App 定位为**个人记录工具（日历/提醒类）**，不给出医学结论，这是能直接上架的前提。若后续加"根据症状建议是否停药"这类功能，性质就变了，需要另议。

## 2. 目标用户与核心场景

典型用户：银屑病 / 强直性脊柱炎 / 类风湿 / 炎症性肠病患者，正在用阿达木单抗、司库奇尤单抗、乌司奴单抗、依奇珠单抗等，**每 1~8 周自我皮下注射一次**。

三个核心场景（也是验收标准）：

1. **该打针了**：周五 9:00 收到"今天该注射了"，打开就是注射登记页，30 秒打完卡。
2. **忘了上次啥时候**：打开首页，一眼看到"上次 10 月 18 日 · 距下次还有 6 天"。
3. **复诊要交记录**：一键导出 6 个月 CSV / PDF，医生能看到日期、药名、剂量、部位、不良反应。

## 3. 信息架构

底部 5 个 Tab（主路径短，日历用于提前查看未来注射安排）：

```
[ 今天 ]  [ 记录 ]  [ 日历 ]  [ 趋势 ]  [ 设置 ]
   │         │         │         │         │
   │         │         │         │         └─ 用药方案 / 提醒设置 / 免打扰 / 应用锁 / 导出 / 免责声明
   │         │         │         └─ 注射时间轴、症状与注射相关性、依从性统计
   │         │         └─ 月视图：未来注射日程、选中日期的药名与剂量
   │         └─ 历史注射列表、症状日志列表、编辑/删除
   └─ 下次注射倒计时卡、今日待办、快速登记 FAB、轮换部位提示
```

首次启动走 3 步 Onboarding：选药（预置常用生物制剂 + 自定义） → 选方案（间隔） → 设定提醒时间，然后进首页。

## 4. 关键流程

### 4.1 登记一次注射

首页 FAB → 底部抽屉：

- 时间（默认现在，可改）
- 药名 / 剂量（预填方案默认值）
- 注射部位（默认给"推荐位点"，可改）
- 可选：备注、批次号

保存后立刻：写入 `injection` → 重算下次时间 → **取消旧提醒并重新排程** → 首页动画更新倒计时。

### 4.2 下次时间怎么算（核心设计决策）

三种锚点策略，默认选 **A**：

| 策略 | 规则 | 适合 |
| --- | --- | --- |
| **A. 实际注射为锚（默认）** | 下次 = 本次实际时间 + 间隔 | 大多数自我注射患者，符合"打完起算"的真实医嘱 |
| B. 计划为锚 | 下次 = 计划时间 + 间隔，不因迟到顺延 | 严格按日历（如每 4 周固定周五） |
| C. 固定日历 | 每月固定某日 | 月度制剂 |

配套**允许偏差窗口**：`±N 天`（默认 ±2），窗口内算"按时"，超出算"提前/延迟"，只在趋势页做统计，不弹警告、不显示红色恐吓性 UI。

逾期处理：超过计划时间未登记 → 首页卡片变"已逾期 X 天"，通知降级为每日上午一条轻提醒（最多 3 天，可关）。

### 4.3 负荷剂量（loading dose）

很多生物制剂首剂有加强方案，例如第 0 / 1 / 2 / 4 周各一次，之后每 12 周维持。方案模型用**阶段列表**表达，而不是写死成特例：

```
阶段 1（负荷）: 从首次注射起，间隔 1 周，共 3 次
阶段 2（维持）: 之后每 12 周 1 次
```

排程引擎按"已完成次数"推进阶段指针，逻辑简单且可扩展到任意方案。

### 4.4 间隔调整与历史补录

医生把 8 周改成 6 周时，不应把过去的 8 周记录按 6 周重算。方案调整采用**阶段生效时间**：

- 旧阶段保留原间隔和历史计数；
- 追加一个带 `effective_from` 的维持阶段，下一针从生效时间起按新间隔排；
- 之后补录生效时间之前的历史注射，仍落在旧阶段、按旧间隔计算。

首次设置时可以录入「上次注射时间」，作为当前方案的真实锚点；注射登记页支持「保存并继续补录」，
方便从纸质记录或旧 App 连续补录历史。

## 5. 数据模型（expo-sqlite + Drizzle）

```ts
// 药物与方案
medication       (id, name, generic_name, default_dose, unit, color, is_builtin, created_at)
regimen          (id, medication_id, name, anchor: 'actual'|'planned'|'calendar',
                  window_days, is_active, created_at)
regimen_phase    (id, regimen_id, order_idx, kind: 'loading'|'maintenance',
                  interval_days, repeat_count, dose, unit)
// 注射记录
injection        (id, regimen_id, medication_id, injected_at, dose, unit,
                  site, lot_number, note, created_at, updated_at)
// 症状
symptom_log      (id, logged_at, severity 1-5, tags: json, note,
                  temperature, injection_id nullable)
// 提醒与偏好
reminder_rule    (id, regimen_id, offsets: json /* [-2,-1,0] 天 */, time_of_day 'HH:mm',
                  snooze_minutes, enabled)
app_setting      (key, value)   // app_lock, theme, locale, dnd_window, disclaimer_accepted_at
```

要点：

- **下次注射时间不落库**，一律由 `injection` + `regimen_phase` 实时推导。避免"改了方案但计划表是旧的"这类经典不一致 bug。
- `site` 存枚举而非自由文本，才能做轮换算法和统计。
- 时间统一存 **UTC 毫秒**，展示时转本地时区。这是提醒类 App 最容易踩的坑（跨时区/夏令时）。

## 6. 提醒策略（本地通知）

用 `expo-notifications` 全部本地调度，不依赖服务器。

**排程窗口**：iOS 对单 App 待发本地通知有约 64 条上限，所以采用**滚动预排 8 周**：

- 每次注射登记 / 方案变更 / App 冷启动 → 清空并重排未来 8 周的通知
- 用 `BackgroundTask` + AppState 回前台时补排

**通知层级**：

| 时机 | 内容 | 可关 |
| --- | --- | --- |
| T-2 天 09:00 | "还有 2 天该注射了（修美乐 40mg）" | 是 |
| T-1 天 20:00 | "明天该注射了，别忘了提前取出冷藏药" | 是 |
| 当天 09:00 | "今天该注射了" + 直达登记页 | 是 |
| 当天 20:00 | 未登记则补一条 | 是 |
| 逾期每日 09:00 | "已逾期 2 天" | 是，最多 3 天 |

细节：

- Android 需要 `SCHEDULE_EXACT_ALARM` / 通知渠道；未授予时降级为普通通知并提示用户去系统设置。
- 免打扰时段（默认 22:00–08:00）内不投递，顺延到次日。
- **冷藏药提示**是这类用户真实痛点，值得单独一条（"提前 30 分钟取出回温"）。
- 通知文案不出现诊断性表述，只说"该注射了"。

## 7. 部位轮换

位点枚举 8 个：腹部左上/右上/左下/右下、左大腿、右大腿、左上臂、右上臂。

推荐算法（每步 O(n)，无需复杂状态）：

1. 候选 = 全部位点
2. 排除最近 2 次用过的位点（避免短期重复）
3. 优先选**历史使用次数最少**的位点
4. 同分时优先与上次**不同侧**（如上次左侧腹部 → 这次右侧）
5. 腹部优先使用（吸收稳定、痛感低），可配置权重

UI 用人体示意图 + 高亮点，点一下即选中。首次使用时说明"腹部需距脐 5cm 以上"。

## 8. 症状日志与趋势

- 快速记录：1–5 级严重度 + 标签（注射部位红肿、发热、乏力、皮疹、关节痛…）+ 备注 + 体温。
- 趋势页做**时间对齐**展示：注射事件竖线叠在症状曲线上，让用户自己看节律（很多生物制剂有"注射后 1–2 天轻微反应"的模式）。
- **明确写"仅用于自我观察，不构成因果判断"** —— 这条文案在合规上是必要的。
- 依从性统计：按时 / 提前 / 延迟比例、平均偏差天数。

## 9. 导出

- **CSV**：全部注射 + 症状原始数据，UTF-8 BOM（Excel 中文不乱码）。
- **PDF 就诊报告**：`expo-print` 生成 HTML→PDF，含患者自填姓名/出生年（可选）、时间范围、注射表格、症状摘要、依从性统计。单向输出，不落云。
- 分享用 `expo-sharing`，生成的文件放 cache 目录，导出后提示"该文件含健康信息，请谨慎分享"。

## 10. 技术选型

| 用途 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | Expo SDK 54 + expo-router | 文件路由、OTA、开发体验 |
| 语言 | TypeScript strict | 医疗数据模型需要类型保护 |
| 存储 | expo-sqlite + Drizzle ORM | 关系清楚、可迁移、比 AsyncStorage 靠谱 |
| 状态 | Zustand + 派生 selector | 轻，不需要 Redux |
| 校验 | Zod | 导入/导出与表单统一校验 |
| 通知 | expo-notifications | 唯一成熟方案 |
| 图表 | react-native-gifted-charts 或 自绘 SVG | 时间轴+曲线 |
| 导出 | expo-print + expo-file-system + expo-sharing | 无服务端 |
| 安全 | expo-local-authentication（应用锁） | 打开需指纹/面容 |
| 测试 | Vitest（纯逻辑）+ 少量组件测试 | 排程引擎必须单测 |

**关键**：排程引擎（`nextDoseAt`、阶段推进、窗口判定）做成**纯函数模块**，与 UI/SQLite 解耦，全量单测。这是这个 App 唯一真正复杂的地方，也是唯一出错会直接影响用户用药时间的地方。

```

  onboarding/

  db/                schema.ts, migrations, repositories
```

## 11. 安全与隐私

- 无网络权限（不加任何 analytics / crash SDK），从根上杜绝外泄。
- 应用锁（生物识别）默认关闭，首次设置时提示开启。
- 卸载即清除；提供"清空全部数据"。
- 导出文件明确警告。
- 商店隐私声明可写"不收集任何数据"。

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **M0** 骨架 | Expo 工程、4 个 Tab、主题、SQLite + Drizzle 建表 | 能跑起来、能建一条数据 |

建议先做 M0+M1（能立刻试用），跑通后再定 M2 的通知细节。

## 13. 需要你确认的 4 个点

1. **锚点策略**：默认用"实际注射时间为锚"（打完起算），你的医嘱是这种吗？
2. **单药还是多药**：只支持一个当前方案，还是同时管理多种/历史停用的药？（数据模型已预留多药，UI 可先简化为单药）
3. **界面语言**：只做简体中文，还是中文 + 英文？
4. **首版预置药名**：要我预置哪些（修美乐/阿达木单抗、可善挺/司库奇尤单抗、拓咨/依奇珠单抗、喜达诺/乌司奴单抗、恩利/依那西普…），还是全部让用户自己填？
